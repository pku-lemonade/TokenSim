# Operator Latency Data Collection Checklist

This checklist lists the measured data the `operator_table` backend needs to
price runs without falling back to analytical estimates. It is organized by
device, operator table, shape grid, and collection method. The tables and
lookup rules are described in [Operator Latency Model](operator-latency-model.md);
the collection scripts are documented in `scripts/collect/README.md`.

After a simulation run, `missing_shapes_<qps>.json` in the result directory
(written whenever a miss was recorded) reports what the tables could not
answer, grouped by table and discrete key with the requested axis ranges and
the reason (`table_absent`, `discrete_key`, `out_of_range`,
`no_measured_mode`, ...). It covers compute
operators and the `collective` / `ep_all2all` communication tables alike and
can be fed directly into the next collection round. Run with
`--latency_fallback table_only` to stop at the first miss instead of falling
back to formulas. Before running a simulation, preview the coverage of a
package for the models and TP sizes you plan to run:

```bash
python -m TokenSim.operator_data.cli coverage \
    --device h100_sxm --backend vllm --models llama-3-8b --tp 1,8
```

Common gaps:

- **`elementwise`**: no measured package has the table, so RMSNorm, RoPE,
  residual additions and SwiGLU are priced analytically in every run.
- **Multi-node collectives**: NCCL curves cover one node; only the SGLang
  DeepEP tables of H100/H200 have multi-node rows.
- **Collective dtype**: TokenSim queries collectives with the model's
  activation dtype. The NCCL curves are fp16 and int8, so bf16 models match
  only the bf16 custom all-reduce rows.
- **Operator modules**: `mhc` is in every H100, H200, B200, B300, GB200 and
  GB300 package, and in L40S (TensorRT-LLM, vLLM) and RTX PRO 6000 (SGLang,
  TensorRT-LLM). `dsv4_attention` is in the vLLM packages of those six
  devices. `dsv4_megamoe` holds SGLang measurements in every B200, GB200 and
  GB300 package; the B200 and B300 vLLM packages use the GB200 and GB300
  tables, and B300 has no measurements of its own.

## 2. Per-Table Collection Requirements

The grids below are recommended sweeps. `operator_data.cli manifest` produces
the exact keys a set of models needs (defaults: decode batches 1-256, prefill
tokens 16-8192, decode contexts 128-32768; see the operator latency model,
section 8).

### 2.1 `gemm`

**Key fields:** `dtype`, `m`, `n`, `k`
**Interpolation axes:** `k` (log), `n` (log), `m` (log)

* **Precision:** one sweep for each weight dtype your models use (`gemm` is
  keyed by the weight dtype: bf16, fp8, fp8_block, int8_wo, int4_wo, nvfp4,
  ...). Check `operator_dtypes` in the model YAML for operators with their own
  dtype (router, LM head, attention projections).
* **`m` (token count):** 1, 2, 4, 8, 16, 32, 48, 64, 96, 128, 192, 256, 384,
  512, 768, 1024, 2048, 4096, 8192, 16384.
  The low-m region must be densely sampled: all decode latencies fall here.
* **`(n, k)` pairs:** determined by the target models and TP degree. The
  `manifest` command expands the projection roles QKV, O, gate-up, down,
  router (MoE models) and LM head. For `llama-7b`, `llama-3-8b`, `llama-3-70b`
  and `llama-2-70b` at TP 1/2/4/8 this yields 57 distinct `(n, k)` pairs.
* **Collection method:** `scripts/collect/run_aiconfigurator.sh` with
  `OPS=gemm`. The AIConfigurator collector benchmarks the serving framework's
  own GEMM kernels and records the selected kernel in the `kernel_source`
  column, which the importer keeps as `kernel`. Its token grid is denser than
  the manifest default (1-17 one by one, then pairs such as 32/33 and 48/49 up
  to 4352/4353, then 8192, 16384 and 32768) to catch tensor-core tile
  boundaries.

### 2.2 `context_attention` (prefill)

**Key fields:** `attn_dtype`, `kv_cache_dtype`, `batch_size`,
`input_seq_len`, `num_heads`, `num_kv_heads`, `head_dim`, `window_size`
**Interpolation axes:** `num_heads` (linear), `batch_size` (log),
`input_seq_len` (log)

* **`input_seq_len`:** 16, 32, 64, 128, 256, 512, 1024, 2048, 4096, 8192,
  16384.
  **`batch_size`:** 1, 2, 4, 8 (total tokens up to 32K).
* **Head configuration:** `(num_heads, num_kv_heads, head_dim)` set to the
  per-rank local values for the target models and TP sizes. For example,
  LLaMA-3-70B at TP 8 yields `(8, 1, 128)`.
* **`attn_dtype`, `kv_cache_dtype`:** the model's activation dtype and
  KV-cache dtype.
* **`window_size`:** 0 (no sliding window). Add the model's window size when
  profiling sliding-window attention.
* **Collection method:** `scripts/collect/run_aiconfigurator.sh` with
  `OPS=attention_context`. The collector uses the framework's attention
  kernels (TRT-LLM fused MHA / XQA, or FlashAttention / FlashInfer with
  `BACKEND=vllm`) and covers bf16 and fp8 KV caches.

### 2.3 `generation_attention` (decode)

**Key fields:** `attn_dtype`, `kv_cache_dtype`, `batch_size`,
`context_len`, `num_heads`, `num_kv_heads`, `head_dim`, `window_size`
**Interpolation axes:** `num_heads` (linear), `batch_size` (log),
`context_len` (log)

* **`context_len`:** 128, 256, 512, 1024, 2048, 4096, 8192, 16384, 32768.
  For long-context experiments, add 65536 and 131072.
* **`batch_size`:** 1, 2, 4, 8, 16, 32, 64, 128, 256 (up to 512 when KV-cache
  capacity allows).
* **Head configuration:** as for `context_attention`. **`kv_cache_dtype`:**
  every KV-cache dtype your models use (bf16, fp8, ...).
* **Collection method:** `OPS=attention_generation`; the collector's decode
  grid spans batch 1-2048 and context 2-131072. Paged-attention kernels are
  what the frameworks run, so no dense-KV baseline is needed.

### 2.4 `moe`

**Key fields:** `dtype`, `distribution`, `num_tokens`, `hidden_size`,
`inter_size`, `top_k`, `num_experts`, `tp_size`, `ep_size`
**Interpolation axes:** `num_tokens` (log)

* **Target models** (catalog entries):
  - `mixtral-8x7b`: E = 8, k = 2, inter = 14336
  - `qwen3-235b-a22b`: E = 128, k = 8, inter = 1536
  - `deepseek-v4-pro`: E = 384, k = 6, inter = 3072, routed experts in mxfp4
* **`num_tokens`:** 1, 2, 4, 8, 16, 32, 64, 128, 256, 512, 1024, 2048, 4096,
  8192, 16384 (tokens entering the layer for the whole EP group).
* **`(tp_size, ep_size)` configurations:** (1,1), (2,1), (4,1), (8,1), (1,8),
  (1,16), (1,32).
* **`distribution`:** `uniform`. To study hot-expert effects, add
  `power_law_1.2` (AIConfigurator's label).
* **Collection method:** `scripts/collect/run_aiconfigurator.sh` with
  `OPS=moe` (TRT-LLM fused MoE, or vLLM `fused_moe` with `BACKEND=vllm`).
  Upstream labels skewed routing `power_law_1.01` / `power_law_1.2`; the
  importer keeps the label in the `distribution` key, and the backend tries
  `uniform`, `balanced`, `power_law_1.01` in turn for uniform routing. Use
  `MODEL_PATH=<hf id>` to restrict the grid to one model's expert shape.

### 2.5 `elementwise`

**Key fields:** `op_name`, `dtype`, `num_tokens`, `hidden_size`
**Interpolation axes:** `hidden_size` (log), `num_tokens` (log)
**Recognized ops:** rmsnorm, layernorm, rope, residual_add, swiglu, gelu,
data_reorder, other_residual

* **`op_name`:** rmsnorm, rope, residual_add, swiglu (for gated FFN layers).
* **`dtype`:** the model's activation dtype.
* **`num_tokens`:** 1 through 16384, using the same grid as the GEMM `m` axis.
  **`hidden_size`:** the model hidden dimension `h`; for rope, use
  `q_local + kv_local`; for swiglu, use `inter_local`.
* **Collection method:** `scripts/collect/collect_elementwise.py`
  (AIConfigurator has no elementwise table). `--kernel eager` times plain
  PyTorch ops; `--kernel vllm` times vLLM's fused `rms_norm` /
  `rotary_embedding` / `silu_and_mul` kernels, the production path, and skips
  `residual_add`. The script merges its rows into the package given by
  `--package`.

### 2.6 `collective`

**Key fields:** `dtype`, `operation`, `group_size`, `nodes`,
`message_bytes`
**Interpolation axes:** `message_bytes` (log)
**Recognized operations:** all_reduce, all_gather, reduce_scatter, all_to_all,
send_recv

* **Operations:** all_reduce (tensor parallelism) is the one the simulator
  queries; all_to_all, all_gather and reduce_scatter complete the picture for
  other layouts.
* **`group_size` x `nodes`:** single node: 2, 4, 8. Multi-node: 16 (2 nodes),
  32, 64; add 128 when available.
* **`message_bytes`:** 1 KiB to 1 GiB in power-of-2 steps.
* **`dtype`:** the model's activation dtype (bf16 for most catalog models;
  nccl-tests `-d bfloat16`).
* **Collection method:** single node: `scripts/collect/run_aiconfigurator.sh`
  (its `collect_comm.sh` step runs nccl-tests for 2/4/8 GPUs in half and int8,
  plus the framework's custom all-reduce). Multi-node:
  `scripts/collect/run_nccl_tests.sh` with `LAUNCHER="mpirun ..."` and
  `DTYPE=bfloat16`; record the NIC model, all NCCL environment variables, and
  the `NCCL_DEBUG=INFO` output showing the selected algorithm/protocol, which
  calibrates the topology's `collective_algorithm`.

### 2.7 `ep_all2all`

**Key fields:** `dtype`, `phase`, `mode`, `ep_size`, `nodes`,
`hidden_size`, `top_k`, `num_experts`, `num_tokens`
**Interpolation axes:** `num_experts` (log), `top_k` (linear),
`hidden_size` (log), `num_tokens` (log)

* **Modes:** `deepep_high_throughput` and `deepep_low_latency`, dispatch and
  combine.
* **`ep_size` x `nodes`:** the EP groups of your clusters: 8 ranks on one node
  for `per_dp` EP8, and the wide groups of `global` EP across nodes.
* **`num_tokens`:** tokens dispatched per rank, from 1 to the largest prefill
  chunk.
* **Collection method:** AIConfigurator's wide-EP collectors (for SGLang the
  `deepep_ll` and `deepep_normal` ops, see the upstream
  `collector/wideep/README.md`). The importer reads their
  `wideep_deepep_{ll,normal}_perf` files as well as `moe_a2a_perf` tables;
  SGLang wide-EP rows record only the node count; their EP size is the node
  count times `--gpus-per-node`, which defaults to the upstream system
  description's `num_gpus_per_node` and is required for a collector run
  directory.

### 2.8 Operator-Module Tables

Complete module tables (`dsv4_attention`, `mhc`, `dsv4_megamoe`) come from
AIConfigurator's module collectors: the `mhc_module` and
`dsv4_{csa,hca}_{context,generation}_module` ops, and the SGLang DeepGEMM
MegaMoE campaign in `collector/sglang/dsv4_megamoe`. The importer reads
`mhc_module_perf`, `dsv4_{csa,hca}_{context,generation}_module_perf` and
`dsv4_megamoe_module_perf` files; `--module-source table=<system dir>` takes a
module from another system and records that in the source notes. Collect
modules on the target device and stack where possible; borrowed rows are
grade B.

### 2.9 Step-Level Fixed Overhead (`step_overhead_us` in device YAML)

* Run a real inference framework with batch 1 and a one-token prompt for
  several decode steps. Subtract the sum of the per-table operator latencies
  from the measured step time to obtain the fixed scheduling and launch
  overhead.
* Every bundled device file sets `step_overhead_us` to 0 (grade D); a
  measured value replaces that assumption.

## 3. Recording Requirements

Besides the key fields and `latency_us`, every CSV or Parquet row carries:

| Field | Description |
| --- | --- |
| `source_id` | Required. A structured identifier naming a `generation_meta.yaml` source entry (e.g. `aiconfigurator:a100_sxm:gemm:trtllm:1.0.0`) |
| `kernel` | Recommended. The kernel or API call name (e.g. `flash_fwd_splitkv_kernel`), needed to trace differences between stacks |

### `generation_meta.yaml` Required Fields

Each package directory must contain a `generation_meta.yaml` file with at
least the following structure:

```yaml
schema_version: 1
latency_unit: us
dataset_version: <device>-<backend>-<tag>
device_id: <device_id>
backend: <backend>
framework_version: <version>

sources:
  - source_id: <unique_source_id>
    grade: A          # A = measured, B = third-party or adjacent device, C = derived, D = analytical
    method: measured  # measured | imported | public_benchmark | analytical | assumption
    reference: <URL or path>
    notes: <free text>
    device: <device_id>
    backend: <framework:version>

calibration: {}

tables:
  gemm:
    rows: <count>
  # ... one entry per table present in the package
```

`source_id`, `grade` and `method` are required for every source; each
`tables` entry must equal the row count of its file. The `notes` of every
source should record:

- **Device model** (as reported by `nvidia-smi`)
- **Driver and CUDA version**
- **Framework and version** (e.g. vLLM 0.24.0, TRT-LLM 1.3.0rc20)
- **Clock lock state** (whether GPU clocks were locked during profiling)
- **Measurement method** (CUDA event median, iteration count)
- **Date and operator** (collection date and the person who performed it)

Run `python -m TokenSim.operator_data.cli validate <package>` after editing a
package.

## 4. Groq Special Case

Direct kernel-level measurement is not possible on the Groq TSP. The following
public data sources are available:

| Data Source | Usage | Grade |
| --- | --- | --- |
| Product Brief v1.5: 750 TOPS INT8, 188 TFLOPS FP16, 230 MB SRAM, 80 TB/s memory bandwidth, 16 chip-to-chip links, PCIe Gen4 | Device catalog specifications | A |
| ISCA 2020 (TSP architecture): 320 lanes, 88 MEM slices, deterministic execution model | Structural assumptions for the analytical model | A |
| ISCA 2022 (RealScale): 4 lanes x 25 Gbps/link, 8 TSPs/node, 9 nodes/rack, 11-link topology | Link class `groq_c2c_25g`, topology `groq_node8_rack72` | A |
| "Accelerating BERT on TSP": batch 1, seq 128, approximately 130 us end-to-end | Layer-level validation: run `bert-base` on a single chip using the `analytical` backend and compare the 12-layer total time | A (paper-grade) |
| GroqCloud public throughput: LLaMA-2-70B approximately 300 tok/s at 576 chips; Mixtral approximately 500-800 tok/s | End-to-end order-of-magnitude check; does not decompose into per-operator times | B |

### Items Requiring Confirmation

- **480 GB/s bandwidth figure:** the device catalog interprets this as
  16 links x 4 lanes x 30 Gbps x 2 directions.
- **Chip-to-chip hop latency:** the catalog assumes 0.5 us per hop.
- **Host-side step overhead:** whether a host scheduling overhead exists in the
  Groq execution model (the TSP's deterministic execution may eliminate it).

### With GroqRack Access

With GroqRack hardware access, use the GroqFlow profiler to collect
single-operator cycle counts for GEMM and attention. Conversion to
microseconds: `cycles x (1 / 900 MHz)`.

## 5. Validation Data (End-to-End Calibration)

End-to-end measurements are not used to populate operator tables, but they
check that the simulator's predictions are in the right order of magnitude.

* **Published framework benchmarks:** vLLM and TensorRT-LLM results for
  LLaMA-3-8B and LLaMA-3-70B on A100/H100. Metrics: TTFT (time to first
  token), TPOT (time per output token), and throughput, broken down by batch
  size and input/output sequence length (grade B).
* **Your own measurements:** run `vllm bench latency` (or the framework's
  equivalent) on the target hardware, simulate the same configuration with
  TokenSim, and compare the prefill and decode median latencies.
