# AgentX 原生混合 HBM 缓存

本次修改完成 GPU 内的 DSV4 分组布局、共享物理池、chunk 分配与原生前缀恢复。SimpleCPU/Mooncake、router、DP 同步和原生算子计时继续按计划分开实施。硬件基线使用 HBM-only，保留现有算子计时；正式参考点的精度验收仍需完成这些后续工作。

## 布局与容量

## 分配与恢复规则

`HybridKVBlockManager` 使用一个共享 free queue：未缓存块放到队首优先复用，已缓存块放到队尾维持 FIFO/LRU 驱逐顺序。每个请求分别记录各组的 logical index 与物理 slot；窗口推进时释放旧引用，已缓存的检查点元数据可以继续留在可驱逐队列中。完成、抢占和取消各自处理引用，取消不会发布尚未计算的内容。

这是完整日志揭示的关键修复。初版把所有释放块都放到 FIFO 队尾，导致短状态页反复分配、驱逐长前缀：两个完整窗口的 GPU 命中率仅为 B200 0.4345%、B300 0.1983%。本地 `BlockPool.free_blocks` 明确将未缓存块 `prepend_n`、已缓存块 `append_n`，`SingleTypeKVCacheManager.free` 则按 tail-first 释放。现在两种优先级和组内顺序都按源码处理。新用例在 1,000-slot 池中分配超过 20,000 次窗口页，仍能恢复原先缓存的前缀；它直接验证状态页循环使用不会无故破坏 APC。

并发请求生成相同前缀时，按照 vLLM `BlockHashToBlockMap` 保留每个有效副本；首个副本被驱逐后，后续副本仍可命中。初版仅保留一个 canonical 副本，会在驱逐时丢失仍然有效的内容。完整运行的 20 秒 CPU 采样还发现，每步重复扫描和发布 full prefix、排序块表占据大量模拟器执行时间。现在 full group 只处理新分配和新计算的区间，块表保持有序插入，未变化时不重建；窗口组继续按实际索引回收。该采样是模拟器 CPU 开销证据，与模拟的 GPU 算子时间分开处理。

完整输入 admission 是容量检查；实际物理分配随 chunk 推进。普通 HBM 同步运行不全局预留后续 chunk；源码中的其他在途 prefill 预留用于异步 CPU 加载，留给 offload 阶段处理。默认 watermark 与本地源码一致为零；显式 watermark 只作用于与已调度请求并存的 admission，不阻止 running 请求使用剩余 slot。

前缀使用模型、回放作用域和哈希链隔离，主引擎将四个原始 64-token hash 聚合成一个完整 256-token hash。短窗口组保留原始 64-token 身份及子块位置。恢复要求 full group 和所有窗口组同时成立，最多恢复 prompt 的 n−1 token，并按引擎边界截断。

MTP SWA 命中检查多看一个块，然后在恢复时丢掉该块，让下一步在私有 slot 中重新计算。retention 的 32,768-token 边界也包含这个 peek；漏掉它会使长前缀的检查点无法恢复。末尾可恢复边界和检测到的共享前缀边界保留窗口状态。decode 为 1+K token 的空间分配各组 slot；MTP 的实际随机进度和成本仍由后续投机解码阶段完成。

## 测试与运行证据

新增 25 个测试覆盖页大小、打包、历史日志等效重建、正预算扣除、完整输入准入与延迟分配、窗口推进、retention、全组命中、EAGLE peek 丢弃、共享引用、重复副本驱逐、增量发布、未缓存块优先复用、缓存尾块优先驱逐、作用域隔离、lookahead、取消，以及完整原生模型进入真实 engine 后的 chunk 完成、物理释放和完整结果结构。动态调度或关闭 chunk 的完整 AgentX 配置会在加载数据前被拒绝。`python -m unittest discover -s tests -v`：341 个测试全部通过，85.814 秒。

一小时管线基线使用全部 393 条 trace、98,827 条原始请求作为负载池，完成预热后发请求 3,600 秒，再执行 30 秒宽限与最多 10 秒取消收尾。最终结果目录为 `results/agentx-dsv4-full/hybrid-cache/20260930-free-queue/{b200,b300}/`，修复前的两个完整窗口保留在 `20260930-validated-pool/`，明确标为诊断。默认流式保存逐请求、回放事件、每分钟缓存窗口以及每 worker 的分组和内存预算；不保证全部原始请求被执行。

## 当前观察与下一步

运行中的窗口证据表明，缓存使用率较低时仍有大量 waiting 请求。B200 模拟 5,220 秒时各 worker 仅有 0–2 个 running；B300 4,680 秒时八个 worker 均只有一个 running，同时各有 38–54 个 waiting。长请求占据整个 8,192/16,384-token step 预算，说明后续必须接入 512-token 长 prefill 限流；单纯增加 KV 容量不能解决这种排队。原生 CSA/HCA/SWA 算子表、MTP、多 rank 同步和路由也会改变这些时长，当前吞吐只能作为管线基线。

现有 `operator_component_seconds` 尚未在预热结束时清零，包含预热及测量累计成本。本报告按回放阶段及成功请求边界记录时间，不将该累计字段解释为正式测量的一小时分解；计时阶段隔离须在后续算子统计工作中修复。
